
[80X86.DOC]
[Harold V. McIntosh, 10 September 1984]

This program was originally written as an exercise for the program-
ming language CNVRT.  Neverthless it was intended to be an exercise
with a practical application, since there are many programs written
for the Intel 8080 which could be used with the Intel 8086 if they
could be converted to the other code.  These two CPU's are very sim-
ilar, since the Intel 8086 was designed with compatibility in mind.

As a practical program 80X86 has been very useful. It handles the
greatest part of the conversion from the Intel 8080 to the Intel
8086, although there are always quite a few details to be modified
by hand.

There is no limit to the work which a translator program could
undertake. Its simplest assignment is to substitute Intel 8086
instructions for the corresponding Intel 8080 instructions. As
compatibility between the two CPU's was intended from the start,
there is almost always a single target instruction with the same
parameter structure for every source instruction. Nevertheless
the correspondence is not exact. With time, certain particular
discrepancies have shown up. In the beginning, say with Sorcim's
TRANS86, which was the model for our original program, only a
few inconvenient sequences were accounted for - their rendition
of xthl, or the equivalents of ldax or stax - which simply did
not have a single byte Intel 8086 equivalent.

On this basis, experience showed that two principal sources of
incompatibility remained. One was the fact that inx, dcx do not
affect flags, while inc, dec do. Thus if a pointer modification
intervened between some arithmetic-logical operation or some
comparison and a later conditional call, jump or return which
depended on it, the program logic would not be correct.

The other frequent source of translation error arose because
the register A is the high byte for pushes and pops for the
Intel 8080, but al is the low byte for the Intel 8086. The
intrinsic form of instructions such as lahf and sahf obliges
the programmer to respect this inversion.

Fortunately these two discrepancies can be corrected by adopting
a slightly more complicated equivalence for the instructions
involved. The result is a translation that will surely work, as
we have verified by trying it on some problem translations. The
drawback is that all this protection is only needed in a minority
of situations. The production of really optimal code is impeded
by the necessity to remove the protection in all the places where
it is not needed.

80X86 has been updated to include this protection.

It is one thing to produce a translation which is conservatively
designed to be technically correct under all circumstances. It
may be less efficient than possible but its reliability makes it
worthwhile.  Turning to efficiency, it is a temptation to combine
Intel 8080 instructions to make use of the extensive addressing
combinations of the Intel 8086, or of the additional registers
available. In this connection, the register si has to be seen as
a more natural counterpart of the register pair DE. To exploit
this extra convenience requires very careful attention to register
usage, which is beyond the scope of the 80X86 program.

Aside from the correspondence between machine language instructions,
there is a difference in philosophies and styles of operation in the
assemblers ASM.COM and ASM86.CMD. The latter relies heavily on the
context to distinguish between byte and word operations, while the
mnenomics of the former make the differences quite explicit. There
are some new assembler directives in ASM86, and some qualifiers,
which are reserved words that might have been used as labels in an
ASM program - byte, wait, ss, dd are some examples. There is also a
difference in acceptance of non-alphanumeric characters - $ vs @ -
to be taken into account.

Although a translation program could filter out these differences
in the two assemblers, mistakes will show up soon enough as errors
denounced by ASM86, from whence they can be corrected by an editor.
Annoying as such retouching may be, people writing programs that
are destined for translation will soon enough learn to avoid using
questionable menmonics. Not considering such things simplifies the
writing of the translator considerably.

80X86 carries out two additional steps which are represented by a
sufficient number of lines of code in most programs to ensure their
value.  One transformation depends on the fact that ASM86 does not
want colons following labels in statements whch define data - db, dw,
rb, and rw.  The reasoning is that the colon places the label in
the code segment, but data will normally go in a data segment.

The other transformation is really an artifact of CP/M, since
access to BDOS in CP/M-86 is through <int E0> rather than <call 5>.
If the programmer has made all his BDOS calls in a standard form
such as <call BDOS>, <call 0005H>, or <call X0005>, these calls
can be picked out and replaced with <int bdos>.

There is really an area which lies in the realm of artificial
intelligence rather than program translation. Suppose, as is often
the case in machine language programs, that the program to be
translated is an assembler or a compiler. Then, a rote translation
will produce a program to handle Intel 8080 code but which will
run on the Intel 8086, which is probably only half of what is
desired. On the one hand, Intel 8080 operation codes included as
data will probably confuse the translator except for the unlikely
case that they have been included as hexadecimal constants. On
the other hand, the program will be built around a whole structure
of operation codes and bit patterns which the translator will know
nothing about. So, let the would-be translator be warned!

Another point to beware in making a translation is that data areas
often begin on special boundaries, to simplify address arithmetic
used to consult the data. In translating from the Intel 8080 to the
Intel 8086 program lengths will change, so that the positioning of
a critical data area may also be changed.

In short, it requires a good knowledge of the program to be trans-
lated, the Intel 8080 machine language, and the Intel 8086 machine
language to make a satisfactory transition from one to the other.
A program such as 80X86 can simplify the transformatiom markedly,
but it can hardly be expected to make the transformation completely
automatic.

80X86 removes colons from data declarations, and calls to BDOS made
in a particular form are translated. Either could be built up further
to suit a particular user or a particular class of programs.

In neither case are equivalences defining CP/M's default file control
block, the default buffer area, or the linkages to CP/M via address
0001 or 0006 recognized. Our experience is that these are best modified
by hand, since they can occur in so many variations. The replacement of

        tfcb:   equ     005CH

by

                org     005CH
        tfcb    rb      0
        tfcb:   equ     005CH

handles the problem quite satisfactorily.  If the programmer has used
good discipline and placed the CP/M linkages together at the front of
his program, an adaptation of this type is quickly made. Don't forget
to include an <bdos equ 0E0H> in the program too.
